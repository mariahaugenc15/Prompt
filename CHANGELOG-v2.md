# Prompt v2 changelog

Everything below shipped as its own commit on `claude/prompt-app-concept-build-iu5wvo`, in phase order. Each phase's commit message has the full detail; this groups the same work by kind for a reviewer, plus what needs to happen outside the code to run it. All 14 phases are now complete (Phase 14 is scoping-only, as the brief asked).

## Design

- **Today highlight** (Phase 2.1): today's calendar cell now gets a distinct terra-cotta outline and a matching soft drop shadow (new `--shadow-today` token), separate from the existing "has completions" cover-photo state, so both can be true on the same day without clashing. Updates itself at local midnight with no app restart.
- **Ambient time-of-day background** (Phase 7.1): every screen now sits in front of a faint, line-work scene that shifts with the time of day (sunrise lines, then sun and trees, then moon/stars/clouds), matching the existing icon stroke style and kept low-opacity enough to never compete with text. Crossfades smoothly between phases; goes fully static under `prefers-reduced-motion`. (Later unmounted from the live app per an explicit, direct request mid-build; the component and its code remain in the repo, just not wired in.)
- **Branded loading indicator** (Phase 7.3): a slowly turning line-work leaf (`LoadingMark`) replaces every plain "Loading..." label app-wide, matching `Icons.tsx`'s stroke style instead of a generic spinner.
- **Tasteful hover affordance** (Phase 7.3): buttons and links lift slightly on hover, scoped to pointer-capable devices so touch and keyboard focus are unaffected.
- **Ink-stamp texture** (Phase 8): a reusable SVG `feTurbulence`/`feDisplacementMap` filter gives every stamp (and the monthly recap's share-image stamp motif) an irregular, hand-pressed border instead of a plain circle.
- **Sticky-note customization** (Phase 9.1): five paper-tone colors (butter, blush, sage, sky, terra-cotta, all contrast-checked against the existing ink color), five line-work stickers, and three handwriting fonts (Caveat, Kalam, Shadows Into Light), all pulled from or matched to the existing palette rather than inventing a new one.

## Functionality

- **Calendar month navigation fixed** (Phase 1.1): Home, the public profile, and calendar detail no longer get stuck unable to see last month once the month rolls over; added prev/next controls bounded to the account's/calendar's own creation date.
- **Continuous scrollable month feed** (Phase 2.2): Home's calendar is now a vertically scrolling stack of months (newest first, lazily loaded) instead of one fixed month, reaching all the way back to the account's creation month.
- **Editable username** (Phase 1.2): `PATCH /api/me/username`, format- and uniqueness-checked server-side, with a configurable cooldown between changes. Every reference elsewhere in the schema is by account id, so a rename never breaks anything already posted.
- **True audio response for "Sound it"** (Phase 1.3): in-app voice recording (record/re-record/playback/submit) instead of reusing the photo/video form, with a server-enforced size cap. The duration cap was initially only a byte-size proxy (a crafted low-bitrate file could stay under the size limit while running far longer); fixed to measure actual decoded duration server-side via `music-metadata`, with an audio player wherever a submission is shown.
- **Three-way reactions** (Phase 3.1): like/dislike/laugh (mutually exclusive) replace the old single upvote; pin stays independent. A visibility check was added to comments and reactions so a private 1:1 completion's comments/reactions can't be read or added to by someone outside that conversation. This same shared check is what Phase 12 later extends to gate sealed content.
- **Expand to see full detail** (Phase 3.1): tapping a card in the feed or a board's submission gallery now opens a detail view with the full comment thread and reaction bar, matching what the day-detail view already showed inline.
- **Notification preferences** (Phase 4): a settings screen with a master switch and one toggle per event, plus an in-app notification list and an unread badge. Push subscriptions are now cleaned up on logout and account deletion. Originally built on four fixed `accounts` columns; migrated to an extensible `(account_id, event)` row-per-preference table so every later phase (monthly recap, sealed reveal, game updates) could add a new notification type without another schema migration.
- **Adult-content board flag** (Phase 5.1): board owners (or an admin) can mark a board 18+. Flagged boards are excluded from Discover/search/cross-board discovery for anyone who hasn't opted in, and joining or reading a flagged board's actual content (subscribe, the challenge/submission gallery, and later the game/leaderboard surfaces) is blocked server-side, not just hidden in the UI.
- **Top Fans leaderboard** (Phase 5.2): board owners can see subscribers ranked by response rate across all boards they run, with a minimum-received threshold so a single lucky completion can't outrank a long consistent history. Owners can optionally publish it; individual accounts can opt out of appearing in it.
- **Permanent account delete** (Phase 6): a separate, stricter action from Ban. Requires re-typing the exact username (checked server-side), deletes the account's own avatar and every row that's purely about that one account, and leaves shared content intact under the anonymized identity so other people's history isn't disrupted.
- **Admin audit log** (Phase 6): every ban, permanent delete, CSV export, suggestion edit, and game disable/enable is recorded (who, whom, when, a short detail string) in a log an admin can review.
- **Contact-all-users broadcast email** (Phase 6): admins can email every non-unsubscribed account from the dashboard, with a required test send, a server-enforced confirm step, batched delivery, a per-recipient unsubscribe link, and a send history.
- **Stamps** (Phase 8): completing a prompt earns a stamp in that category instead of a plain dot on the calendar. A stamp book page shows all five categories (earned with a count, or a locked silhouette), gated by the same visibility check 1:1 completions already use so a stranger can't see a private exchange's stamps. Haptic + sound feedback at the moment of earning one, both independently toggleable, honoring `prefers-reduced-motion`.
- **Sticky-note customization + corkboard home** (Phase 9): a sender can style a 1:1 prompt's note (color/sticker/handwriting, all optional and collapsed behind one control) before sending, rendered identically on the home screen, the send animation, day detail, and the expanded view. Home's single note was replaced with a corkboard grid of every unfinished received prompt.
- **"Need an idea?" prompt generator** (Phase 10): a shuffle button on Send a prompt and a board's Broadcast form suggests a prompt matched to category and a chosen pack (Chill/Brave/Silly/Outdoors), never repeating one already seen this session. 120 suggestions (above the 100 minimum), stored as data and editable from the admin panel without a release.
- **Monthly recap** (Phase 11): a server-computed summary (completions, completion score, favorite category, longest streak, most-laughed-at response, top exchange partner) for each month once it ends, cached permanently since a past month's figures never change. Exportable as a share image (9:16 or 1:1) through the system share sheet; the exported image never includes the top friend's username or any other user's content, only the account's own aggregates.
- **Group prompts + sealed reveals** (Phase 12): Send a prompt now supports 2-10 recipients in one group, with an optional "Sealed" toggle (everyone's answers hidden until the last person finishes or a deadline passes, whichever first). Sealed content is invisible to everyone but its own author until reveal, including the sender, enforced at one shared gate used by every feed, calendar, and the comments/reactions check. Reveal runs as a server job (immediate on the last completion, swept for passed deadlines every minute), is idempotent, and a late completion after reveal is marked as such. Stamps are still awarded on completion regardless of seal state.
- **Weekly leaderboard game** (Phase 13.2): a board owner can turn on a weekly game (timezone-aware week boundary, points for completions with an early-finish and category-variety bonus, a daily cap against spamming). Shows the top three, the viewer's own rank, and everyone's participation; an owner can hide ranks entirely, leaving just participation visible. Awards a "Week winner" stamp and keeps every past week's history.
- **Team challenge** (Phase 13.3): a board owner splits current members into two or more randomly-shuffled teams for a fixed period; team score is the average per member so uneven team sizes are fair. Awards a "Team winner" stamp to the winning team at the end of the period.
- **Event prompts** (Phase 14): scoping only, as the brief asked. See `docs/event-prompts-proposal.md`. Nothing from it is built.

## User Experience

- UI copy sweep for consistent wording across empty states, errors, and settings (part of every phase above, and a final dedicated pass, see "Final notes" below).
- Push permission and notification settings are now self-service and discoverable from a bell icon with an unread badge, instead of being silent or all-or-nothing. Every new event type (monthly recap, sealed reveal, game updates) gets its own toggle in the same screen.
- The adult-content gate shows a clear, tap-to-confirm interstitial rather than silently hiding content, once an account has opted in at the profile level; the same gate now also covers a board's game/leaderboard surfaces.
- A sealed group prompt shows a clear "waiting on the others" state (with a progress count) to a recipient who's already answered, and a plain sealed card with a prompt to answer to one who hasn't, rather than either looking like an ordinary pending prompt.

## Admin Panel

- New **Broadcast** tab: compose, preview, send a test to yourself, and send to everyone, with send history.
- New **Audit Log** tab: a running record of admin actions (ban, delete, export, suggestion changes, game moderation).
- New **Delete** action next to Ban on the accounts table, gated by a username-confirmation prompt.
- New **Suggestions** tab (Phase 10): view, add, inline-edit, and enable/disable "Need an idea?" library entries by category and pack, no release required.
- New **Games** tab (Phase 13.4): view every board with a game turned on, and disable or re-enable one for moderation independently of its owner's own toggle.

## Animations

- **Send-a-prompt animation rewritten** (Phase 7.2): the sticky-note send animation is now a slower, more deliberate ~2 second sequence (a squiggle draws in as if still being written, the note creases as if folding, then peels free and arcs off-screen) instead of the old 1.1 second lift-and-arc. Falls back to a plain fade under `prefers-reduced-motion`, and never blocks navigating away mid-animation.
- **Ambient background animation** (Phase 7.1): gentle, slow drift/arc/twinkle per time-of-day scene, static under `prefers-reduced-motion`. (See the Design section note: later unmounted from the live app.)
- **Loading indicator animation** (Phase 7.3): the leaf mark turns slowly while active, static under `prefers-reduced-motion`.
- **Stamp moment** (Phase 8): a press-overshoot and ink-bloom settle animation plays the instant a stamp is earned, with haptic and sound feedback, falling back to a simple fade under `prefers-reduced-motion`.
- **Corkboard settle** (Phase 9.2): received notes animate into place with a small spring and a per-note tilt when the corkboard first loads, honoring `prefers-reduced-motion`.
- **Sealed reveal** (Phase 12.4): the first time a viewer opens an already-revealed sealed prompt, the responses fan onto the card with a staggered entrance ("the seal is broken"); a later visit to the same, already-seen reveal shows the normal static list. Honors `prefers-reduced-motion`.

## Fun and Engagement

- **Stamps** (Phase 8) and the **Stamps book** page replace plain completion dots with a real, collectible per-category mark.
- **Sticky-note customization** (Phase 9) turns every sent prompt into something the recipient can make visually their own, rather than one fixed look.
- **"Need an idea?"** (Phase 10) removes the blank-text-box moment from sending a prompt.
- **Monthly recap** (Phase 11) gives a reason to open the app on the 1st, and something shareable.
- **Sealed reveals** (Phase 12) turn a group prompt into a small, synchronized reveal moment instead of a stream of individual notifications.
- **Weekly leaderboard and team challenge** (Phase 13) give a board's regulars a lightweight, non-shaming competitive reason to keep completing prompts together.

## Migrations to run

None by hand. Every schema change in this release is either a `CREATE TABLE IF NOT EXISTS` (new installs) or a defensive `ALTER TABLE ADD COLUMN`/table-rebuild with a safe default, run automatically by `server/db.ts` the next time the server starts, against the existing production database. New columns/tables added this release, by phase:

- **Phase 1-6**: `accounts.username_changed_at`; `boards.is_adult`, `boards.top_fans_public`; `completion_reactions` rebuilt to widen its reaction-kind constraint from `('upvote','pin')` to `('like','dislike','laugh','pin')` (every existing "upvote" row carried over as "like"); new tables `notifications` (see below for a second rebuild), `admin_audit_log`, `broadcast_emails`.
- **Phase 4 (notification prefs)**: the four original fixed `accounts.notify_*` columns were superseded by a new `notification_prefs(account_id, event, enabled)` table, backfilled once from any account that had explicitly disabled something under the old columns; the old columns are kept as read-only backfill source, never written to again.
- **Phase 8 (Stamps)**: new tables `stamp_definitions` (seeded with one evergreen definition per category) and `user_stamps`, backfilled once for every completion that existed before this shipped so v1 history shows stamps immediately.
- **Phase 9 (note styling)**: `prompts.note_color`, `note_sticker`, `note_handwriting`, all nullable (NULL = the original unstyled look).
- **Phase 10 (suggestions)**: new table `prompt_suggestions`, seeded from `server/data/promptSuggestions.json` (120 rows) on every boot via `INSERT OR IGNORE`, so an admin's later edits in the live table are never overwritten by a redeploy.
- **Phase 11 (monthly recap)**: new table `monthly_recaps` (a permanent cache, since a past month's figures never change) and a generic `job_runs` idempotency ledger used by every scheduled job added from this phase onward.
- **Phase 12 (group prompts)**: `prompts.group_id` (nullable; NULL means an ordinary 1:1 prompt, unchanged), and a new `prompt_groups` table holding each group's sealing/deadline/reveal/cancellation state.
- **Phase 13 (games)**: new tables `board_games`, `game_weeks`, `game_opt_outs`, `game_rank_snapshots`, `team_challenges`, `challenge_teams`, `challenge_team_members`; one additional `stamp_definitions` row each for `week_winner` and `team_winner`.
- **Bug fix found during Phase 12/13 verification**: `notifications.event` shipped in Phase 4 with a CHECK constraint hardcoded to its original 3 event types, which crashed the first time Phase 11's `monthly_recap` or Phase 12's `sealed_reveal` event actually fired. The table was rebuilt (same pattern as the `completion_reactions` rebuild above) to drop the CHECK constraint entirely; `notificationsRepo.ts`'s `NotificationEvent` TypeScript union is the real, extensible source of truth for valid events from here on.

No existing data is altered destructively anywhere in this list; a deploy is the only step required.

## Manual steps

- **Email (SMTP)**: the Phase 6 broadcast feature sends through the same `emailer.ts` used for password resets. If SMTP env vars aren't set in production, broadcast sends (like password-reset emails already did) just log to the server console instead of actually sending. Set real SMTP credentials before relying on Broadcast.
- **Push (VAPID / APNs)**: no new requirement from this release beyond what v1 and the earlier visible-push work already needed; Phase 4 only adds preference gating in front of sends that already existed, and every later phase's push (recap, sealed reveal, game updates) reuses that same existing send path.
- **Admin access**: the Broadcast, Audit Log, Suggestions, and Games tabs all sit behind the existing `ADMIN_USERNAMES` env var and admin role, nothing new to configure there.
- **Scheduled jobs**: Phase 11's monthly recap push, Phase 12's sealed-reveal sweep, and Phase 13's weekly/game-check/team-challenge sweeps all run inside the existing single web process via a new in-process scheduler (`server/scheduler.ts`), on a plain `setInterval`. No external cron, queue, or second process needs to be provisioned; this only becomes a correctness concern if the app is ever run as more than one web instance, which it isn't today (`render.yaml` provisions exactly one).
- No new required environment variables were introduced by this release.

## Final notes: anything not completed or done differently

- **Phase 5.1 (adult content)**: the brief's "hidden from users who are not verified adults" has no age-verification mechanism to hook into anywhere in this codebase, and building one is out of scope for this phase. What's implemented is the one concrete mechanism the brief actually describes: a user-level opt-in (default off). "Verified adult" stays aspirational until there's an age-verification flow to attach it to.
- **Phase 5.2 (Top Fans)**: the ranking is computed across every board a given owner runs (per the brief's "on that owner's boards"), while the public/owner-only display toggle is a per-board setting, since that's the only place in the existing UI with an owner context.
- **Phase 2.2 (scrollable month feed)**: "paginate so long histories stay fast" is handled by lazily rendering additional months client-side, rather than adding server-side activity pagination.
- **Phase 4 (push)**: handling the browser's `pushsubscriptionchange` event for silent token refresh isn't implemented; an expired subscription is cleaned up lazily on its next failed send instead.
- **Phase 7.1 (ambient background)**: built and then deliberately un-mounted from the live app per an explicit request made directly during this build. This was not reverted; the component remains in the repo, unused.
- **Phase 9.2 (corkboard ordering)**: "soonest-expiring most prominent" wasn't implemented since no expiry concept exists for an ordinary prompt (that's Phase 12's sealed-reveal deadline, a different mechanism entirely); ordering is newest-first instead.
- **Phase 9 (note styling scope)**: broadcasts never get note styling; the styling control only ever appears on a 1:1 send, and a broadcast's note fields are always explicitly null rather than left ambiguous.
- **Phase 12.1 (group prompts, data model)**: reuses the existing `prompts` table exactly as the brief suggested ("if the data model already supports multiple recipients, reuse it"): a group prompt is N ordinary 1:1-shaped rows sharing one `group_id`, not a new parallel structure.
- **Phase 12.5 (edge cases)**: a recipient who can no longer act (deleted/banned) just leaves their row waiting on the deadline, same as an unresponsive 1:1 recipient today; blocks are checked only at send time, matching existing 1:1 behavior, and don't retroactively hide an already-revealed joint response; completions can't be edited or deleted anywhere in this app, so "a response edited or deleted while sealed" doesn't apply; a cancelled group never reveals, and whatever any author already submitted stays visible only to them forever; deadlines are a fixed millisecond offset from send time (never calendar-relative), so time zones and daylight saving never move them; and the recipient list is fixed at send time, with no add/remove-later support.
- **Phase 13.1 (reuse decision, documented as asked)**: a board, not Phase 12's `prompt_groups`, is the group container for both the weekly game and the team challenge. A `prompt_groups` row is scoped to one single prompt with no lasting membership, the wrong shape for an ongoing game; a board already has an owner who can configure it, a persistent member list, and an existing 18+ flag to extend.
- **Phase 13.2/13.3 (stamp reuse)**: "Week winner" and "Team winner" reuse the Phase 8 stamp system at the data layer exactly as asked (same tables, same award-once idempotency), but are deliberately not added to the `Category` type or the Stamps book's 5-category grid, since that grid's own visibility check assumes a stamp's `completion_id` is a real completion row, which a week or challenge id isn't. They surface instead from the game's own leaderboard/standings UI.
- **Phase 13.3 (team challenge + sealed reveals)**: "optionally use sealed reveals from Phase 12" is not built. A board broadcast and a Phase 12 group prompt are structurally different rows with no existing bridge between them; team challenge prompts are plain, unsealed board broadcasts.
- **Phase 13.4 (game notification throttling)**: the four game notification types share one "Group game updates" toggle rather than one each, and "you were passed" is throttled by construction (a once-a-day rank-snapshot comparison), not a cooldown timer layered on top of a check that could otherwise fire on every completion.
- **Phase 14 (event prompts)**: scoping only, as asked. See `docs/event-prompts-proposal.md`. Nothing from it is built.
- **Ground Rule 4 (no em dashes)**: the final sweep rewrote every em dash found in UI copy, error messages, empty states, an email body, a dev log line, shareable meta tags, the suggestion library, and recap/stamp/game copy. Code comments (pre-existing and newly added, never shown to a user) and `README.md`/`docs/*.md` (developer documentation, not in-app content) were reviewed and deliberately left alone as outside "app language." Three literal em-dash placeholder glyphs in the admin panel's tables (standing in for "no value" in a cell) were swapped for an en dash (–) rather than removed, since that's a visual convention rather than sentence punctuation.
